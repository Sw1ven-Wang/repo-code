# 通用能力与任务绑定（2026-11-12）

## 三层契约

1. **能力模板**：问题机制、可观察的触发与排除条件、决策步骤、检查与未知边界，以及带语义用途的绑定槽位。模板不保存训练题路径或固定测试命令。
2. **应用绑定**：当前 Run、已送达的能力契约、授权 route、当前源码摘要、已读文件版本、具体工具参数和适用理由。由 Host 签名并单独保存为 `capability_binding`，不修改能力模板。
3. **应用与验收证据**：绑定之后真正执行的工具操作、结果、独立验收。`BOUND` 不等于 `applied`，`applied` 不等于 `verified`，更不等于通用收益已获证明。

## 提炼与发布

`ProcedurePromotion` 的新版提炼提示和 schema 要求抽象 `binding_slots`。真实模型新生成的无槽位方案会被拒绝为 `PROMOTION_PORTABLE_PLAN_REQUIRED`。历史 prepared plan 与离线旧协议夹具保留兼容性，但不会自动变成通用能力。

每个槽位包括 `kind`（`path` 或 `argv`）与语义 `purpose`。例如：

```json
{
  "binding_slots": {
    "implementation": {
      "kind": "path",
      "purpose": "定位根据子节点状态决定是否重建容器的当前实现，并检查数值相等与元数据相等是否被混淆。"
    },
    "verification": {
      "kind": "argv",
      "purpose": "根据当前项目测试配置确定验证命令，覆盖状态传播、数值不变量及未变化输入。"
    }
  },
  "step_rules": [
    {"tool": "read", "arguments_match": {"path": {"slot": "implementation"}}},
    {"tool": "edit", "arguments_match": {"path": {"slot": "implementation"}}},
    {"tool": "process.run", "arguments_match": {"argv": {"slot": "verification"}}},
    {"tool": "workspace.diff", "arguments_match": {"path": {"slot": "implementation"}}}
  ]
}
```

槽位必须全部使用，类型必须与工具参数匹配；混入固定参数、未知槽位或多余字段均拒绝。当前首版支持 read/edit/workspace.diff 的 path 和 process.run 的 argv；任意 patch 数组、create 内容及多文件批量动作模板尚未开放，不能伪称已支持。

Host 对提炼结果中的已知支持任务文件名做确定性排查；独立语义 reviewer 继续检查是否混入固定命令、特定结构、训练答案或未经证实的前提。字符串排查不是通用语义证明。历史文件版本留在来源证据里，新候选不把它们误作后续仓库必须存在的文件；原语义/环境 preconditions 保留，新任务另做已读版本绑定。只有通过独立审查的候选才进入后续实验。

S1 继续绑定模板、候选 Release 和探针；S2 仍要求真实执行支持任务及正负/边界探针；S3 对 portable 能力增加不同文件布局的 TRANSFER 要求，且保留原独立实现、负例、退化、成本及真实模型收益条件。布局变化只是额外必要条件，并不单独证明任务独立或语义泛化。G3/G4/G4b、Release 审批、激活机制未被替代。

## 原生调用流程

1. Host 在授权 scope 内，根据已经提供的机制级 `task_family`、触发事实和排除条件检索已授权能力。
2. 路由将通用模板、`contract_ref`、`route_id` 和调用说明送达模型；维持既有一次送达、不重复注入语义。
3. 模型读取当前实现、测试或配置，形成任务适配方案。
4. 模型调用 `skill.bind`，填写每个槽位的实际值、支持它的已读路径及机制适用理由。路径槽位必须引用该文件自身；命令槽位必须引用已读取的测试/配置依据。
5. Host 检查 offer、当前授权、撤销、scope 间接绑定、control epoch、当前文件版本、路径安全、槽位类型及覆盖，保存不可变签名绑定。理由是待核查的模型判断，不被当成已证实事实。
6. 模型执行正常工具。`skill.bind` 与后续操作可位于同一模型响应中，实际操作仍逐项走 Broker 权限、版本、预算和沙箱控制；绑定不会代执行命令或授予权限。
7. 回执使用本 Run 的解析后规则匹配绑定之后的成功操作。绑定前的探查不能被追认为执行；匹配命令也必须成功退出。独立、当前源码的可信验收证据仍决定 verified。

具体文件和命令只进入 `capability_binding` 与操作轨迹，不回写发布模板。完整 diff 等价覆盖证明继续沿用原实现。

## 边界与兼容性

- Memory v1 默认不变；不重构 Episode 或 Evidence Selector。
- `scope` 仍是授权边界，不能为方便复用改成通配。任务族必须表示问题机制，不能以仓库名称冒充；本轮没有实现自动机制分类器。
- 跨项目需在被授权范围内建立目标项目绑定；换环境需要相应重新验证。新 state-root 仍需可信导入/准入流程，不能复制旧签名或复活已撤销 grant。
- 本轮新增的是结构化能力的 `skill.bind`，没有把旧 `skill.search` 的知识检索接口改造成新的授权入口。
- 有效模板也可能在新任务中不适用。没有适用能力时回退基线。没有候选时应在实验预检中报告零覆盖，不把这种实验解释成能力收益 A/B。
- 旧固定参数 contract 的序列化摘要保持兼容，不给历史 Release 或经验修改内容、追认通用性或补签资格。
- 未经独立真实质量验证不得自动发布。离线脚本即使完整跑通，也只能证明接入与证据链，不能证明模型提升。

## 验证与恢复

专项包含不同路径下相同模板的应用、实际失败→修改→本地/Docker 测试通过、无授权/未读取/过期版本/路径越界/缺槽拒绝、签名破坏、跨 Run 冒用、事务失败回滚、重启恢复、控制 epoch 失效，以及同布局迁移拒绝。

绑定按 Run + route + contract 幂等；事务中断不会保留半条绑定或事件。已成功绑定不能被模型悄悄改写。需要不同适配方案时由 Host 决定新的授权尝试，不通过覆盖历史记录“修好”统计。
